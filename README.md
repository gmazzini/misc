# misc

`misc` contains small standalone utilities that do not belong to a larger project.

Current contents:

- `runtelnet.c` - small Telnet command runner, currently Version 1.02;
- `file.c` - small CGI file store, currently Version 1.5;
- `photo.c` - photo archive CGI and console manager, Version 3.04;
- `photo.db` - SQLite photo catalogue imported from the historical database;
- `Makefile` - portable build file for all utilities in this directory;
- locally built executables are generated by `make`.

## runtelnet

`runtelnet` opens a Telnet connection to a host, performs the login sequence, sends one or more commands and waits for the remote prompt between commands.

It was written primarily for MikroTik RouterOS, but the network connection itself accepts either IPv4 or IPv6 addresses or host names through `getaddrinfo()`.

The program uses TCP port 23.

### Syntax

```sh
runtelnet host user password "command" ["command" ...]
```

Example:

```sh
./runtelnet 2001:db8::1 admin password \
    "/system resource print" \
    "/interface print" \
    "/quit"
```

Each command is a separate command-line argument. Quoting each RouterOS command is recommended so spaces and shell metacharacters are not interpreted by the local shell.

There is deliberately no special separator character inside the command string.

### Session sequence

The current sequence is:

1. connect to TCP port 23;
2. wait for the `login:` prompt;
3. send the user name;
4. wait for the `password:` prompt;
5. send the password;
6. wait for the RouterOS command prompt;
7. send each command in command-line order;
8. wait for the RouterOS prompt before sending the next command.

`/quit` is not inserted automatically. If a clean RouterOS logout is wanted, pass `/quit` explicitly as the last command:

```sh
./runtelnet router admin password "/system resource print" "/quit"
```

This keeps every remote action visible in the command line and allows the caller to decide exactly which commands are sent.

If the final command is `/quit`, the remote side is expected to close the connection and that is treated as normal completion.

### Telnet protocol handling

`runtelnet` implements the small amount of Telnet negotiation required for this use case. It recognizes Telnet IAC negotiation sequences and refuses unsupported options instead of passing negotiation bytes to the prompt parser.

It does not depend on an external `telnet` executable.

### Output

Login and password prompts are consumed internally. Command output received after login is written to standard output.

Errors are written to standard error and the program returns a non-zero exit status on connection, protocol, prompt, send or receive failures.

### Timeout

The current receive timeout is 15 seconds for each wait operation.

This is intended to avoid leaving the program blocked indefinitely if the remote system does not answer or if the expected prompt is not received.

## file

`file` is a small CGI file store intended to run behind Apache. A single executable handles all operations and selects the command from the first component of `REQUEST_URI`.

The command is the part before the first `.` or `/`, therefore these are equivalent:

```text
/up
/up.php
/up.anything
```

The implemented commands are:

- `up` - upload one or more files;
- `dw` - download the current version;
- `dwold` - download an archived version;
- `del` - archive and remove the current version;
- `ls` - list current files;
- `lsold` - list archived files.

All requests use HTTP `POST` with `multipart/form-data`, preserving the interface of the previous PHP implementation.

Examples:

```sh
curl -4 -X POST https://file.chaos.cc/up -F "id=xxx" -F "label=@file"
curl -4 -X POST https://file.chaos.cc/dw -F "id=xxx" -F "name=label" -o out.xxx
curl -4 -X POST https://file.chaos.cc/dwold -F "id=xxx" -F "name=label" -F "date=YYYYMMDDHHMMSS" -o out.xxx
curl -4 -X POST https://file.chaos.cc/del -F "id=xxx" -F "name=label"
curl -4 -X POST https://file.chaos.cc/ls -F "id=xxx"
curl -4 -X POST https://file.chaos.cc/lsold -F "id=xxx"
```

For uploads, the multipart field name is the logical file name. In the example above the uploaded file is stored as `label`, independently of the local source file name.

### Storage

The default storage root is:

```text
/home/www/file/rep
```

Each identifier has this layout:

```text
rep/id/
rep/id/_old_/
```

Current files are stored directly under `rep/id/`. When an existing file is replaced or deleted, it is moved to `_old_` using:

```text
name.YYYYMMDDHHMMSS
```

If that timestamp already exists, the timestamp is advanced by one second until a free name is found. The historical name format therefore remains unchanged and no version is overwritten.

The storage root can be changed at compile time with `FILE_ROOT`, for example:

```sh
make CPPFLAGS='-DFILE_ROOT="/srv/file/rep"'
```

Operations on the same identifier use filesystem locking to prevent concurrent CGI requests from losing archived versions.

### Apache CGI

Apache only needs to route requests to the single executable. A typical HTTPS virtual-host fragment is:

```apache
ScriptAliasMatch "^/.*$" "/home/www/file/file"

<Directory /home/www/file>
  Require all granted
</Directory>
```

With this mapping, Apache handles HTTP and TLS while `file` receives the request through the standard CGI environment and standard input.

The existing PHP storage directories are directly compatible; no data migration is required.

## photo

`photo` is the Version 3.04 replacement for the photo archive that started in 2004. The historical year is preserved in the source header:

```c
// Gianluca Mazzini @2004- Version 3.04
```

The program uses SQLite and the database path is embedded in the source as `/home/tools/mcp/work/misc/photo.db`. There is no configuration file. This deliberately allows the web installation to be only a symbolic link to the executable in `misc`, with no duplicate database or executable.

The imported database contains 353 records from the historical `myphoto` table. The new schema adds an integer `id` primary key for simple administration while preserving the historical uniqueness of `(album, year1, year2)`. The existing `flag` field is retained and is used to hide records without deleting them.

### Public web interface

When executed by a CGI server (`GATEWAY_INTERFACE` is present), `photo` opens the embedded database path explicitly read-only and serves only the public catalogue. There are no web administration functions, users, passwords, cookies or sessions.

The historical query style remains supported:

```text
/photo?rel=2017
/photo?rel=all
/photo?lookup=luna
```

`year` is also accepted as an alias for `rel`. The page provides a year bar, album search and a responsive card layout. Album links open the stored external photo URL.

All query parameters are bound through SQLite prepared statements and dynamic HTML is escaped before output. Hidden records (`flag != 0`) never appear in the public view.

For an additional Unix-level safety boundary, the deployed CGI user can be given read-only permission on `photo.db`; console administration can then be performed by a different user with write permission.


### Web installation with a symbolic link

The intended deployment does not copy the executable or database into the web root. Create only a symbolic link:

```sh
ln -s /home/tools/mcp/work/misc/photo /home/www/mazzini/photo
```

The CGI always uses `/home/tools/mcp/work/misc/photo.db`, independently of the path through which the executable was invoked. All directories from `/home` through `misc` must therefore be traversable by the Apache user, and `photo` plus `photo.db` must be executable/readable respectively.

### Console management

Administration is deliberately performed from the shell, not from the web interface.

Initialize a new database, or safely ensure that an existing database has the required table and indexes:

```sh
./photo init
```

`init` is non-destructive and idempotent. It creates `photo.db` when missing and uses `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` when it already exists. Existing rows are never deleted or reset. Database creation is deliberately explicit: normal commands do not silently create an empty database if the configured path is wrong.

List all records:

```sh
./photo list
```

Search album names by substring:

```sh
./photo search Luna
```

`search` is case-insensitive and is equivalent to SQL `LIKE '%Luna%'`. The older `./photo list Luna` form is retained for compatibility.

The list reports the numeric ID and `V` for visible or `H` for hidden records.

Add an album:

```sh
./photo add "Album name" "https://photos.example/..." 2026
./photo add "Album name" "https://photos.example/..." 2025 2026
```

Edit one field of an existing album by ID:

```sh
./photo edit 123 album "New album name"
./photo edit 123 url "https://photos.example/..."
./photo edit 123 year1 2026
./photo edit 123 year2 0
```

Only the selected field is changed. Valid editable fields are `album`, `url`, `year1` and `year2`. `year1` cannot be zero; `year2=0` means that there is no second year.

Hide or show a record:

```sh
./photo hide 123
./photo show 123
```

Delete a record permanently:

```sh
./photo delete 123
```

`hide` is preferable when a record may be needed again; `delete` removes it from SQLite permanently. Every write operation is a single SQLite statement and is therefore atomic.

### SQLite schema

The database is based on:

```sql
CREATE TABLE photo (
    id INTEGER PRIMARY KEY,
    album TEXT NOT NULL,
    url TEXT NOT NULL,
    year1 INTEGER NOT NULL,
    year2 INTEGER NOT NULL DEFAULT 0,
    flag INTEGER NOT NULL DEFAULT 0,
    UNIQUE(album, year1, year2)
);
```

Indexes are present for album, both year fields and flag.

## Build

`runtelnet` and `file` use only normal system interfaces. `photo` additionally requires SQLite 3 development headers and library (`sqlite3.h` and `libsqlite3`).

Build with:

```sh
make
```

Clean with:

```sh
make clean
```

The default build compiles all programs. The relevant commands are equivalent to:

```sh
cc -O2 -Wall -Wextra -std=gnu89 -o runtelnet runtelnet.c
cc -O2 -Wall -Wextra -std=gnu89 -o file file.c
cc -O2 -Wall -Wextra -std=gnu89 -o photo photo.c -lsqlite3
```

A different compiler can be selected normally through `make`, for example:

```sh
make CC=clang
```

Compiler flags can also be replaced by the caller:

```sh
make CFLAGS="-O3 -Wall -Wextra -std=gnu89"
```

The Makefile intentionally uses the standard `CC`, `CFLAGS`, `CPPFLAGS`, `LDFLAGS` and `LDLIBS` variables to make rebuilding on other Unix-like platforms straightforward.

## C programming style

Programs in this directory follow the project C conventions:

- C89-style source;
- build in `gnu89` mode because `//` comments are required;
- variables declared at the beginning of functions or blocks;
- variables of the same type grouped where readable and semantically appropriate;
- initialization after declaration;
- prefer `for` to `while` where practical;
- comments in English and only with `//`;
- prefer standard library and system functions over unnecessary helpers;
- performance and memory use are design constraints;
- no unused variables, functions or dead code;
- opening brace on the same line as the statement, with one space before `{`;
- source release number is incremented for every effective code change.

Source headers preserve the initial development year of each utility and use the form:

```c
// Gianluca Mazzini @<initial year>- Version x.yy
```

For example, `photo` preserves 2004 as its initial year.
