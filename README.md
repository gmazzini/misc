# misc

`misc` contains small standalone utilities that do not belong to a larger project.

Current contents:

- `runtelnet.c` - small Telnet command runner, currently Version 1.02;
- `file.c` - small CGI file store, currently Version 1.5;
- `photo.c` - photo archive CGI and console manager, Version 3.04;
- `photo.db` - SQLite photo catalogue imported from the historical database;
- `redirect.c` - wildcard redirect CGI and SMS-authenticated management portal, Version 2.04;
- `redirect.db` - SQLite redirect catalogue;
- `smsauth.c` - generic SMS authentication CGI and console manager, Version 1.10;
- `smsauth.db` - SQLite SMS authentication state;
- `Makefile` - portable build file for all utilities in this directory;
- locally built executables are generated by `make`.

## runtelnet

`runtelnet` opens a Telnet connection to a host, performs the login sequence, sends one or more commands and waits for the remote prompt between commands.

It was written primarily for MikroTik RouterOS, but the network connection itself accepts either IPv4 or IPv6 addresses or host names through `getaddrinfo()`.

The program uses TCP port 23.

### Syntax

```sh
runtelnet host user password "command" ["command" ...]
```

Example:

```sh
./runtelnet 2001:db8::1 admin password \
    "/system resource print" \
    "/interface print" \
    "/quit"
```

Each command is a separate command-line argument. Quoting each RouterOS command is recommended so spaces and shell metacharacters are not interpreted by the local shell.

There is deliberately no special separator character inside the command string.

### Session sequence

The current sequence is:

1. connect to TCP port 23;
2. wait for the `login:` prompt;
3. send the user name;
4. wait for the `password:` prompt;
5. send the password;
6. wait for the RouterOS command prompt;
7. send each command in command-line order;
8. wait for the RouterOS prompt before sending the next command.

`/quit` is not inserted automatically. If a clean RouterOS logout is wanted, pass `/quit` explicitly as the last command:

```sh
./runtelnet router admin password "/system resource print" "/quit"
```

This keeps every remote action visible in the command line and allows the caller to decide exactly which commands are sent.

If the final command is `/quit`, the remote side is expected to close the connection and that is treated as normal completion.

### Telnet protocol handling

`runtelnet` implements the small amount of Telnet negotiation required for this use case. It recognizes Telnet IAC negotiation sequences and refuses unsupported options instead of passing negotiation bytes to the prompt parser.

It does not depend on an external `telnet` executable.

### Output

Login and password prompts are consumed internally. Command output received after login is written to standard output.

Errors are written to standard error and the program returns a non-zero exit status on connection, protocol, prompt, send or receive failures.

### Timeout

The current receive timeout is 15 seconds for each wait operation.

This is intended to avoid leaving the program blocked indefinitely if the remote system does not answer or if the expected prompt is not received.

## file

`file` is a small CGI file store intended to run behind Apache. A single executable handles all operations and selects the command from the first component of `REQUEST_URI`.

The command is the part before the first `.` or `/`, therefore these are equivalent:

```text
/up
/up.php
/up.anything
```

The implemented commands are:

- `up` - upload one or more files;
- `dw` - download the current version;
- `dwold` - download an archived version;
- `del` - archive and remove the current version;
- `ls` - list current files;
- `lsold` - list archived files.

All requests use HTTP `POST` with `multipart/form-data`, preserving the interface of the previous PHP implementation.

Examples:

```sh
curl -4 -X POST https://file.chaos.cc/up -F "id=xxx" -F "label=@file"
curl -4 -X POST https://file.chaos.cc/dw -F "id=xxx" -F "name=label" -o out.xxx
curl -4 -X POST https://file.chaos.cc/dwold -F "id=xxx" -F "name=label" -F "date=YYYYMMDDHHMMSS" -o out.xxx
curl -4 -X POST https://file.chaos.cc/del -F "id=xxx" -F "name=label"
curl -4 -X POST https://file.chaos.cc/ls -F "id=xxx"
curl -4 -X POST https://file.chaos.cc/lsold -F "id=xxx"
```

For uploads, the multipart field name is the logical file name. In the example above the uploaded file is stored as `label`, independently of the local source file name.

### Storage

The default storage root is:

```text
/home/www/file/rep
```

Each identifier has this layout:

```text
rep/id/
rep/id/_old_/
```

Current files are stored directly under `rep/id/`. When an existing file is replaced or deleted, it is moved to `_old_` using:

```text
name.YYYYMMDDHHMMSS
```

If that timestamp already exists, the timestamp is advanced by one second until a free name is found. The historical name format therefore remains unchanged and no version is overwritten.

The storage root can be changed at compile time with `FILE_ROOT`, for example:

```sh
make CPPFLAGS='-DFILE_ROOT="/srv/file/rep"'
```

Operations on the same identifier use filesystem locking to prevent concurrent CGI requests from losing archived versions.

### Apache CGI

Apache only needs to route requests to the single executable. A typical HTTPS virtual-host fragment is:

```apache
ScriptAliasMatch "^/.*$" "/home/www/file/file"

<Directory /home/www/file>
  Require all granted
</Directory>
```

With this mapping, Apache handles HTTP and TLS while `file` receives the request through the standard CGI environment and standard input.

The existing PHP storage directories are directly compatible; no data migration is required.

## photo

`photo` is the Version 3.04 replacement for the photo archive that started in 2004. The historical year is preserved in the source header:

```c
// Gianluca Mazzini @2004- Version 3.04
```

The program uses SQLite and the database path is embedded in the source as `/home/tools/mcp/work/misc/photo.db`. There is no configuration file. This deliberately allows the web installation to be only a symbolic link to the executable in `misc`, with no duplicate database or executable.

The imported database contains 353 records from the historical `myphoto` table. The new schema adds an integer `id` primary key for simple administration while preserving the historical uniqueness of `(album, year1, year2)`. The existing `flag` field is retained and is used to hide records without deleting them.

### Public web interface

When executed by a CGI server (`GATEWAY_INTERFACE` is present), `photo` opens the embedded database path explicitly read-only and serves only the public catalogue. There are no web administration functions, users, passwords, cookies or sessions.

The historical query style remains supported:

```text
/photo?rel=2017
/photo?rel=all
/photo?lookup=luna
```

`year` is also accepted as an alias for `rel`. The page provides a year bar, album search and a responsive card layout. Album links open the stored external photo URL.

All query parameters are bound through SQLite prepared statements and dynamic HTML is escaped before output. Hidden records (`flag != 0`) never appear in the public view.

For an additional Unix-level safety boundary, the deployed CGI user can be given read-only permission on `photo.db`; console administration can then be performed by a different user with write permission.


### Web installation with a symbolic link

The intended deployment does not copy the executable or database into the web root. Create only a symbolic link:

```sh
ln -s /home/tools/mcp/work/misc/photo /home/www/mazzini/photo
```

The CGI always uses `/home/tools/mcp/work/misc/photo.db`, independently of the path through which the executable was invoked. All directories from `/home` through `misc` must therefore be traversable by the Apache user, and `photo` plus `photo.db` must be executable/readable respectively.

### Console management

Administration is deliberately performed from the shell, not from the web interface.

Initialize a new database, or safely ensure that an existing database has the required table and indexes:

```sh
./photo init
```

`init` is non-destructive and idempotent. It creates `photo.db` when missing and uses `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` when it already exists. Existing rows are never deleted or reset. Database creation is deliberately explicit: normal commands do not silently create an empty database if the configured path is wrong.

List all records:

```sh
./photo list
```

Search album names by substring:

```sh
./photo search Luna
```

`search` is case-insensitive and is equivalent to SQL `LIKE '%Luna%'`. The older `./photo list Luna` form is retained for compatibility.

The list reports the numeric ID and `V` for visible or `H` for hidden records.

Add an album:

```sh
./photo add "Album name" "https://photos.example/..." 2026
./photo add "Album name" "https://photos.example/..." 2025 2026
```

Edit one field of an existing album by ID:

```sh
./photo edit 123 album "New album name"
./photo edit 123 url "https://photos.example/..."
./photo edit 123 year1 2026
./photo edit 123 year2 0
```

Only the selected field is changed. Valid editable fields are `album`, `url`, `year1` and `year2`. `year1` cannot be zero; `year2=0` means that there is no second year.

Hide or show a record:

```sh
./photo hide 123
./photo show 123
```

Delete a record permanently:

```sh
./photo delete 123
```

`hide` is preferable when a record may be needed again; `delete` removes it from SQLite permanently. Every write operation is a single SQLite statement and is therefore atomic.

### SQLite schema

The database is based on:

```sql
CREATE TABLE photo (
    id INTEGER PRIMARY KEY,
    album TEXT NOT NULL,
    url TEXT NOT NULL,
    year1 INTEGER NOT NULL,
    year2 INTEGER NOT NULL DEFAULT 0,
    flag INTEGER NOT NULL DEFAULT 0,
    UNIQUE(album, year1, year2)
);
```

Indexes are present for album, both year fields and flag.

## redirect

`redirect` Version 2.04 is both the public `*.chaos.cc` redirect engine and the authenticated management portal. The same executable selects the behavior from `HTTP_HOST`:

```text
www.chaos.cc       -> management portal
<anything>.chaos.cc -> HTTP redirect
```

`www` is reserved and cannot be selected as a user shortcut. The intended final deployment is a wildcard `*.chaos.cc` virtual host on the same server, with DNS moved to the production host only after local/offline validation.

The production database path is:

```text
/home/tools/mcp/work/misc/redirect.db
```

### Redirect records and statistics

Existing redirect rows are preserved. Version 2.04 extends each row with:

- `last_hit`: Unix epoch of the most recent counted request;
- `created`: creation epoch for new rows;
- `updated`: most recent management change.

Historical rows receive zero for fields that cannot be reconstructed. From migration onward every normal redirect request atomically increments `hit` and stores the current epoch in `last_hit`. Requests marked as browser prefetch still redirect but do not change either statistic.

The authenticated portal shows, for the current owner only, the shortcut, destination, description, hit count and last-hit time. It also shows per-user summary statistics: number of shortcuts, total hits, shortcuts used in the last seven days and most recent use.

### SMS authentication and callback

`redirect` uses `smsauth` through a dedicated channel, normally named `redirect`. The normal authentication path is callback-based:

```text
browser -> redirect -> smsauth start
                    <- challenge + OTP
user sends OTP by SMS
SMS gateway -> smsauth
redirect <- signed HTTPS callback from smsauth
browser -> redirect auth check
browser <- redirect session cookie
```

`redirect` does not poll the `smsauth status` API during normal operation. The callback is the authoritative delivery mechanism; `status` remains available in `smsauth` as a recovery/diagnostic interface.

The callback is received by the same `redirect` CGI on `www.chaos.cc`. Its raw JSON body is verified with HMAC-SHA256 using the channel callback secret and the `X-Smsauth-Signature` header. A bad signature is rejected. A database failure returns an HTTP error so `smsauth` does not consider the callback successfully delivered.

A pending authentication stores only the data required to connect browser and SMS challenge: local login token, `smsauth` challenge ID, mobile number, OTP shown to the user, SMS destination number, creation/expiry time and state. An already-pending challenge for the same mobile number is reused rather than opening multiple simultaneous OTP challenges.

### Application sessions

After a successful callback, the browser performs a local `auth_check` against `redirect`. `redirect` then creates its own application session; `smsauth` never creates or owns the portal session.

Session properties:

- 256-bit random server-side session token;
- session cookie is `Secure`, `HttpOnly` and `SameSite=Strict`;
- cookie has no persistent expiry, so it is a browser-session cookie;
- server-side idle timeout is one hour and slides while the portal is used;
- every state-changing form also requires a separate 256-bit CSRF token;
- logout deletes the server-side session and clears the cookie.

### Privacy and conditions of use

The management login identifies `chaos.cc` as a short-URL redirection service and requires the user to acknowledge the privacy notice and accept the conditions of use before SMS authentication starts. The notice is served by the same executable through `/?privacy=1`, so no additional web document or Apache mapping is required.

The notice identifies Gianluca Mazzini as data controller and describes the data actually processed by the current implementation: mobile number, temporary authentication/session data, shortcut, destination, description, aggregate hit count and last-hit time. It also explains purposes and legal bases, retention, technical session cookies, recipients, data-subject rights and the right to complain to the Italian Data Protection Authority.

The application does not retain a per-visitor redirect history, visitor IP address, user agent or referrer. Network/hosting components may still transiently process technical connection data required to provide and secure the service.

The conditions make the authenticated user responsible, within the limits permitted by law, for shortcuts, destination URLs, descriptions and linked content. Phishing, malware, fraud, unlawful content, unauthorized personal data, credentials, tokens, secrets and confidential information are expressly prohibited. The operator may suspend or remove abusive, dangerous or unlawful redirects.

### Generic and advanced users

Any mobile number that successfully authenticates becomes a `generic` user automatically. Existing owner numbers found during database migration are also imported as `generic` without changing their links.

A generic user can create new shortcuts only through the random eight-character generator.

An `advanced` user may additionally choose the label before `.chaos.cc`. Advanced status is controlled only from the console by mobile number. Manual labels use strict ASCII DNS-label syntax: letters, digits and `-`, maximum 63 characters, with no leading/trailing `-`. `www` is reserved.

The `origin` column remains a case-insensitive SQLite primary key. Manual creation therefore uses the database constraint itself as the final atomic uniqueness check: if another user already owns the requested shortcut, or another request wins the race before commit, the existing row is never overwritten.

Web updates and deletes always include both `origin` and authenticated owner mobile number in the SQL predicate. One user therefore cannot modify or delete another user's redirect even by changing hidden form fields manually.

### SQLite runtime tables

Besides the `redirect` table, Version 2.04 uses:

- `users` for mobile number and `generic`/`advanced` mode;
- `sessions` for application session and CSRF tokens;
- `auth_pending` for in-progress SMS authentication;
- `settings` for `smsauth` endpoint/channel/API key/callback secret.

The `smsauth` channel API key and callback secret must remain available to `redirect`, so they are private runtime configuration stored in `redirect.db`. The database and its rollback journal must therefore never be published.

SQLite uses a persistent rollback journal (`redirect.db-journal`) with a 3-second busy timeout. In production Apache needs write access to `redirect.db` and `redirect.db-journal`, but not to the whole `misc` directory.

### Console management

Migration/initialization is non-destructive and idempotent:

```sh
./redirect init
```

Existing redirect rows and hit counters are preserved. Missing Version 2.04 columns/tables/indexes are added, and existing owner mobile numbers are imported as generic users.

Redirect administration remains available from the console:

```sh
./redirect list
./redirect show origin
./redirect search text
./redirect stats [limit]
./redirect add origin destination [description] [cell]
./redirect edit origin field value
./redirect delete origin
```

User mode is managed only from the console:

```sh
./redirect user list
./redirect user advanced cell
./redirect user generic cell
```

`smsauth` integration is configured with:

```sh
./redirect smsauth show
./redirect smsauth set https://www.mazzini.org/smsauth redirect api_key callback_secret
```

`show` reports only whether the private values are configured; it does not print them. `init` never replaces an existing `smsauth` configuration.

The corresponding `smsauth` channel must use the same API key and callback secret and, in the final wildcard deployment, callback to the management host, normally:

```text
https://www.chaos.cc/
```

## smsauth

`smsauth` is a generic SMS possession-authentication service written in C with SQLite. It is intentionally independent from any individual application: `redirect` and future local or remote services use it through named channels.

Current source release:

```text
// Gianluca Mazzini @2026- Version 1.10
```

### Responsibility boundary

`smsauth` proves that a user can send an SMS from a given mobile number. It does not create or manage the caller application's login session.

A typical application flow is therefore:

1. the application asks `smsauth` to start a challenge for a mobile number;
2. `smsauth` returns a challenge ID, a five-digit OTP, the SMS destination number and the TTL;
3. the application shows the OTP and destination number to the user;
4. the user sends the OTP by SMS;
5. the trusted SMS gateway forwards the received SMS to `smsauth`;
6. `smsauth` matches mobile number and OTP and changes the challenge state;
7. the application obtains the terminal result through `status` or an optional callback;
8. after `OK`, the application may create its own session cookie/token and allow all operations required by that application without another SMS authentication until that session expires.

This separation is deliberate: SMS possession authentication is reusable, while session lifetime and permissions belong to each application.

### Single HTTP endpoint

The intended public endpoint is a single URL:

```text
https://www.mazzini.org/smsauth
```

There are no separate `/start`, `/status` or `/incoming` endpoints. All operations are HTTP POST requests to the same URL.

The deployed executable is intended to be exposed by a symbolic link such as:

```text
/home/www/mazzini/smsauth -> /home/tools/mcp/work/misc/smsauth
```

Apache must execute that file as CGI. The executable itself always uses the database in the `misc` directory; the web-root path is only the CGI entry point.

### Start a challenge

An application starts authentication with:

```text
action=start
channel=<channel>
cell=<mobile number>
key=<channel API key>
```

The channel key can also be supplied through the supported HTTP API-key headers.

A successful response has this form:

```json
{
  "result":"PENDING",
  "challenge":"0123456789abcdef0123456789abcdef",
  "code":"58321",
  "expires":90,
  "number":"..."
}
```

Properties:

- `challenge` is a cryptographically random 128-bit identifier represented as 32 hexadecimal characters;
- `code` is a cryptographically generated five-digit OTP;
- `expires` is the configured TTL for the channel;
- `number` is the configured SMS receiving number that the application should show to the user.

The OTP is not an Internet-side password. The application displays it to the user, who must send it through the SMS network.

### Read challenge status

An application can query:

```text
action=status
channel=<channel>
challenge=<challenge id>
key=<channel API key>
```

Logical results are:

```text
PENDING
OK
KO / wrong_code
KO / timeout
```

Status is rate-limited to one request every 100 ms per challenge. Applications should normally poll much more slowly; about once per second is sufficient for an interactive login page.

`status` never accepts an OTP. This prevents an Internet client from brute-forcing the five-digit code against the status interface.

### Incoming SMS gateway POST

The trusted SMS gateway sends JSON to the same endpoint. The relevant fields are:

```json
{
  "key":"<gateway key>",
  "from":"+39...",
  "text":"12345"
}
```

`action=incoming` is accepted but optional. A valid request containing `from` and `text` is automatically treated as an incoming SMS.

Additional JSON fields sent by the Android SMS Forwarder application, including timestamps and SIM information, are ignored.

The sender number is normalized before matching. In particular, an Italian mobile number supplied with the leading country code `39` is normalized to the same internal form used by application challenges.

The first five characters of `text` must be decimal digits and are interpreted as the OTP.

### SMS Forwarder compatibility

The production Android SMS Forwarder application sends a POST without `Content-Length`.

`smsauth` explicitly supports both forms:

- a conventional CGI POST with `CONTENT_LENGTH`;
- a POST with no `CONTENT_LENGTH`, read from standard input until EOF.

The maximum accepted body is 8192 bytes.

Support for the second form is required: it was verified with real SMS traffic and must not be removed during later cleanup.

### Challenge matching and states

Internal states are:

```text
PENDING
OK
WRONG
TIMEOUT
```

A matching active `(cell, code)` challenge becomes `OK`.

If no code matches but exactly one still-active `PENDING` challenge exists for that mobile number, that challenge becomes `WRONG`.

If more than one unmatched active challenge exists for the same mobile number, `smsauth` does not arbitrarily fail one of them.

An incoming SMS for which no relevant challenge exists is accepted at the gateway level but is not stored as an application record.

Expired pending challenges become `TIMEOUT` when normal service activity processes expiration. There is no separate daemon or timer process, so timeout alone does not cause an unsolicited callback at the exact expiry second.

Challenges are one-use records. Old challenge records are periodically purged after approximately seven days.

### Channels

Each application uses a named channel containing:

- channel name;
- SHA-256 hash of the application API key;
- optional HTTPS callback URL;
- callback HMAC secret;
- TTL;
- enabled/disabled flag.

Create a channel with:

```sh
./smsauth channel add name callback_url [ttl]
```

Use `-` instead of a callback URL when the application will use only `status`:

```sh
./smsauth channel add myapp - 90
```

Creation prints a newly generated API key and callback secret. The plaintext API key is not stored and therefore cannot later be recovered; it can only be rotated.

Channel API keys are stored only as SHA-256 hashes. Callback secrets remain stored because `smsauth` must know the original secret to calculate future HMAC signatures.

### Gateway authentication

The SMS gateway uses a separate shared secret from every application channel.

Configure an existing secret with:

```sh
./smsauth gateway set key
```

or generate a new one with:

```sh
./smsauth gateway generate
```

Only its SHA-256 hash is stored in SQLite. Hash comparison uses constant-time comparison logic.

The gateway secret, channel API keys and callback secrets are separate credentials and must not be reused for one another.

### SMS receiving number

Configure one or more SMS receiving numbers with:

```sh
./smsauth number set 3294296486
./smsauth number set '3294296486,3331234567,+393401234567'
./smsauth number show
```

Numbers are stored as a normalized comma-separated list. Spaces around separators are removed; every entry must contain 7 to 15 digits and may start with `+`. The `start` API remains backward compatible and returns the list in the existing `number` string field. A client therefore sees a single number when one is configured, or a comma-separated list when multiple receiving numbers are available. Authentication of the SMS sender itself comes from the `from` value supplied by the authenticated gateway.

### Optional callback

A channel may have an HTTPS callback URL. Plain HTTP callbacks are rejected.

When an incoming SMS changes a challenge to a terminal state, `smsauth` POSTs a JSON result to that callback. The body is signed with HMAC-SHA256 and the hexadecimal signature is supplied in:

```text
X-Smsauth-Signature
```

Callback redirects are disabled, the protocol is restricted to HTTPS and the current connection/overall timeout is five seconds.

A successful HTTP 2xx response marks the callback as completed. A channel configured with `-` has no callback and remains `CALLBACK=no` in listings.

Applications that do not need push delivery can use `status`; this is the intended simple integration for the `redirect` web portal.

### SQLite database

The production database is:

```text
/home/tools/mcp/work/misc/smsauth.db
```

The principal tables are:

- `settings` - service settings such as gateway hash and SMS receiving number;
- `channels` - application credentials and configuration;
- `challenges` - challenge identifiers, numbers, OTPs, timestamps and state.

The database is application state, not an SMS archive. Raw SMS messages are not retained by `smsauth` after normal processing.

`smsauth.db` and `smsauth.db-journal` contain private runtime state and must not be published to GitHub or distributed with the source. Only the source, build file and documentation belong in the public repository.

The temporary raw request dump used during development has been completely removed from Version 1.09. There must be no `smsauth.raw` production log containing SMS bodies or credentials.

### SQLite rollback journal and permissions

SQLite uses a persistent rollback journal:

```text
smsauth.db
smsauth.db-journal
```

These are not two databases. `smsauth.db-journal` is SQLite transaction machinery used to keep writes atomic and recoverable.

`smsauth` explicitly applies:

```sql
PRAGMA journal_mode=PERSIST;
PRAGMA synchronous=NORMAL;
PRAGMA foreign_keys=ON;
```

on every database opening. Setting `PERSIST` only during `init` is insufficient because SQLite journal mode must be correct for each CGI connection.

Keeping the journal file persistent is important for the deployment permission model: Apache needs write access to the database and the already existing journal, but the whole `misc` directory does not need to be writable by Apache.

The verified deployment permissions are equivalent to:

```text
smsauth.db          mcp:www-data 664
smsauth.db-journal  mcp:www-data 664
```

The journal must already exist with suitable ownership/permissions before Apache needs to perform a write transaction.

### CLI management

Current console interface:

```sh
./smsauth init
./smsauth gateway set key
./smsauth gateway generate
./smsauth number set number
./smsauth number show
./smsauth channel list
./smsauth channel add name callback_url [ttl]
./smsauth channel delete name
./smsauth channel key name
./smsauth channel secret name
./smsauth channel callback name callback_url
./smsauth channel ttl name seconds
./smsauth channel enable name
./smsauth channel disable name
./smsauth challenge add channel cell
./smsauth challenge list [limit]
```

`challenge add` is an administration/testing convenience that creates a challenge directly from the console and prints its OTP. Normal applications use HTTP `action=start`.

`channel key name` rotates the API key and prints the new plaintext key. It does not display the previous key.

### Security properties

The current design intentionally provides the following boundaries:

- OTP generated with OpenSSL `RAND_bytes` and rejection sampling;
- 128-bit random challenge identifier;
- OTP accepted only from the authenticated SMS gateway, never from `status`;
- independent application-channel API keys;
- independent SMS-gateway secret;
- constant-time comparisons for credential hashes;
- one-use challenge with short configurable TTL (10 to 600 seconds, normally 90);
- HTTPS-only preconfigured callback destinations, preventing a caller from choosing an arbitrary callback URL during `start`;
- HMAC-SHA256 callback authentication;
- no callback redirect following;
- no raw SMS archive or production raw-request dump;
- SQLite prepared statements and atomic transactions;
- persistent journal allowing a restricted Apache filesystem permission model.

### Verified end-to-end behavior

The production-style path has been tested with a real SMS Forwarder request:

```text
application challenge
        -> five-digit OTP
        -> user SMS
        -> Android SMS Forwarder
        -> https://www.mazzini.org/smsauth
        -> gateway authentication
        -> mobile-number normalization
        -> number + OTP challenge match
        -> SQLite transaction
        -> STATE = OK
```

The same testing exposed and fixed two deployment-specific issues that are now requirements of the design:

1. SMS Forwarder may omit `Content-Length`, therefore EOF body reading is required;
2. SQLite must use the persistent journal on every CGI database opening, otherwise Apache may be unable to recreate a deleted journal inside a non-writable project directory.

At Version 1.10 the raw debugging facility remains removed, the real SMS path has reached `OK`, SQLite integrity has been verified and the journal persists correctly.

## Build

`runtelnet` and `file` use only normal system interfaces. `photo` requires SQLite 3 development headers and library. `redirect` and `smsauth` require SQLite 3, libcurl and OpenSSL.

Build with:

```sh
make
```

Clean with:

```sh
make clean
```

The default build compiles all programs. The relevant commands are equivalent to:

```sh
cc -O2 -Wall -Wextra -std=gnu89 -o runtelnet runtelnet.c
cc -O2 -Wall -Wextra -std=gnu89 -o file file.c
cc -O2 -Wall -Wextra -std=gnu89 -o photo photo.c -lsqlite3
cc -O2 -Wall -Wextra -std=gnu89 -o redirect redirect.c -lsqlite3 -lcurl -lcrypto
cc -O2 -Wall -Wextra -std=gnu89 -o smsauth smsauth.c -lsqlite3 -lcurl -lcrypto
```

A different compiler can be selected normally through `make`, for example:

```sh
make CC=clang
```

Compiler flags can also be replaced by the caller:

```sh
make CFLAGS="-O3 -Wall -Wextra -std=gnu89"
```

The Makefile intentionally uses the standard `CC`, `CFLAGS`, `CPPFLAGS`, `LDFLAGS` and `LDLIBS` variables to make rebuilding on other Unix-like platforms straightforward.

## C programming style

Programs in this directory follow the project C conventions:

- C89-style source;
- build in `gnu89` mode because `//` comments are required;
- variables declared at the beginning of functions or blocks;
- variables of the same type grouped where readable and semantically appropriate;
- initialization after declaration;
- prefer `for` to `while` where practical;
- comments in English and only with `//`;
- prefer standard library and system functions over unnecessary helpers;
- performance and memory use are design constraints;
- no unused variables, functions or dead code;
- opening brace on the same line as the statement, with one space before `{`;
- source release number is incremented for every effective code change.

Source headers preserve the initial development year of each utility and use the form:

```c
// Gianluca Mazzini @<initial year>- Version x.yy
```

For example, `photo` preserves 2004 as its initial year.
